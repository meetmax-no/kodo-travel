# i18n-beslutning — Ko|Do · Flow

**Bruk den avhengighetsfrie `t()`-motoren via `@kodo/shared` — ikke next-intl.**

Hvorfor: ingen dependency, full kontroll, deles på tvers av apper (samme `t()` i
Flow + bankboks), og matcher [i18n-lint-sperren](./i18n-lint-gate.md) perfekt
(flat JSON-paritet + hardkodet-streng-sjekk). Norsk-først + engelsk holder;
app-typene trenger ikke ICU.

---

## Konvensjon — koden kommer fra `@kodo/shared`

Motoren eies av `@kodo/shared` og **reimplementeres aldri per app**:

- **Ren logikk** fra `@kodo/shared`:
  - `translate(key, locale, dicts)`
  - `Locale`
  - `flattenDict`
  - `LOCALE_META`
  - fallback: `dict[locale][key] ?? dict.no[key] ?? key`
- **React-delen** fra `@kodo/shared/ui`:
  - `LocaleProvider`
  - `useLocale()` → `{ t, locale, setLocale, available }`

Appen bidrar kun med:

- egne dict-JSON-er (`no.json` / `en.json`, **flat** struktur)
- wirer `<LocaleProvider dicts={…}>` **én gang**

`t()` tar **kun en nøkkel** (ingen interpolasjon) → komponer tall/verdier med
`t()`-deler.

## Slik drar prosjektet inn `@kodo/shared`

`@kodo/shared` er et GitHub-repo — **`meetmax-no/kodo-shared-repo`** — med **rå
TypeScript og ingen byggesteg**. Next.js transpilerer den rett inn i prosjektet
(«kompileres inn»), så du slipper en publisert npm-pakke.

1. **`package.json`** — dra inn direkte fra GitHub:
   ```jsonc
   "dependencies": {
     "@kodo/shared": "github:meetmax-no/kodo-shared-repo#main"
   }
   ```
2. **`next.config.mjs`** — la Next transpilere den rå TS-en:
   ```js
   const nextConfig = { transpilePackages: ["@kodo/shared"] };
   export default nextConfig;
   ```
3. Pakken bruker Tailwind (`clsx` + `tailwind-merge`, `tokens.css`). Bruker du
   UI-delen, importer `@kodo/shared/tokens.css` i global CSS.

> Repoet er **public**, så `github:`-dependencyen fungerer på Vercel uten token.
> Blir det privat senere, må Vercel/CI ha lesetilgang (deploy-token / git-integrasjon).

### Wiring (én gang)

```tsx
// app/providers.tsx
"use client";
import { LocaleProvider } from "@kodo/shared/ui";
import no from "@/lib/locales/no.json";
import en from "@/lib/locales/en.json";

export function Providers({ children }: { children: React.ReactNode }) {
  return <LocaleProvider dicts={{ no, en }}>{children}</LocaleProvider>;
}
```

```tsx
// bruk i en klient-komponent
"use client";
import { useLocale } from "@kodo/shared/ui";

const { t, locale, setLocale, available } = useLocale();
// <h1>{t("common.title")}</h1>
```

### Tilgjengelig API

- **Logikk** (`@kodo/shared`): `translate`, `Locale`, `LOCALES`,
  `DEFAULT_LOCALE`, `LOCALE_META`, `flattenDict`, `Dict` / `Dicts`,
  `isValidLocale`, `resolveInitialLocale`, `matchNavigatorLocale`.
- **React** (`@kodo/shared/ui`): `LocaleProvider`, `useLocale`,
  `LanguagePicker`, `SettingsShell`, `SettingRow`, `SettingsConfig`.

App-en bidrar **kun** med flate `lib/locales/no.json` + `en.json` og wirer
`<LocaleProvider>` én gang — motoren reimplementeres aldri lokalt.

## Locale-oppstart (SSR vs. klient)

`LocaleProvider` er SSR-trygt og oppfører seg slik:

- **Server (SSR):** rendrer alltid `DEFAULT_LOCALE` (`no`) — kanonisk språk.
- **Klient (mount):** `useEffect` korrigerer til lagret valg → tenant-default →
  `navigator.language` → `no`. Valget lagres i `localStorage` (`kodo-locale`).

Konsekvens: en fersk besøker med engelsk nettleser ser først norsk HTML, så
bytter siden til engelsk ved hydrering (et kort «blink» er mulig). Dette er
**forventet, ikke en feil** — og forklarer hvorfor et automatisk verktøy (f.eks.
en headless nettleser som melder `en-US`) lander på engelsk uten at du rører
flagg-velgeren.

## Nøkkel-konvensjon

- Generisk / delt: `common.*` / `settings.*`
- App-spesifikk: `<appnavn>.*`
- **Config peker på nøkler, i18n eier teksten.**
- **Server-ruter** → send feil-/status-**KODE**, oversett med `t()` i klienten.

## Når er next-intl verdt byttet?

Kun ved:

- tunge flertalls-/ICU-behov
- i18n i **server-komponenter**
- **locale-i-URL**-routing

Ellers: hold deg til `@kodo/shared`.
